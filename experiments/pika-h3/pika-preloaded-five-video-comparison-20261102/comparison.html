Does preloading make Pika INT8 or FP8 faster?

Persistent quantized adapter files, GPU-resident weights, and prepacked merge matrices. Each configuration uses the same production Pika path and the same INT8 ConvRot H3 base. BF16 labels refer to the original BF16 Pika adapter path.

FP8: 0.95% more time than fresh BF16 (0.9906×). INT8: 0.09% more time than fresh BF16 (0.9991×). These are measured full-request differences across the five fixed videos.

What was actually tested

Each process starts after three consecutive idle GPU checks. For FP8 and INT8, 416 quantized weight tensors and their FP32 scales are loaded onto the GPU before timing. Merge RHS matrices are also prepacked. The measured requests perform no adapter weight quantization or CPU-to-GPU adapter weight transfers. Activation quantization remains dynamic.

FP8 uses E4M3 operands and torch._scaled_mm(use_fast_accum=False), returning BF16 bypass activations and FP32 merge deltas. INT8 uses the concrete comfy_kitchen CUDA backend with per-row INT8 activation quantization and INT8 CUTLASS/cuBLAS multiplication; merge deltas use torch._int_mm with INT32 accumulation and FP32 rescaling. No BF16 compute fallback is implemented in either quantized adapter.

Every quantized request applied 208 adapters, executed 458 bypass calls and 150 fused-fc2 merge calls, and made 1,066 native quantized GEMMs. The existing bypass-versus-merge split, sampler, three steps, seed, prompts, input images and audio, dimensions, and output encoding were preserved. The base is unchanged throughout.

Timing limits: one measured request per animal and configuration. Differences of a few seconds may reflect normal run-to-run variation. These results establish the observed effect of this implementation on this GPU; they do not establish a universal FP8 or INT8 speedup.
